# ADR 0001 — bash 3.2 as the language baseline

Status: accepted (2026-08-04)

## Context

The tool has to run on whatever a machine already has. Its whole premise is
that it assumes nothing about the host — so the language it is written in
cannot be something the user has to install first, or the premise fails at the
first line.

macOS ships bash **3.2.57** from 2007 and, for licensing reasons, will not ship
a newer one. Anything written to bash 4+ syntax runs on Linux and dies on a Mac
with a syntax error rather than a diagnosable failure.

## Options considered

**Python.** Comfortable, but not universally present, and version-fragmented in
exactly the way this tool exists to avoid. A `python3` that is missing, too old,
or an externally-managed environment is a real failure mode on the systems this
targets.

**Go.** A static binary would be excellent, and would end the portability
question outright. It also means a build step, a release pipeline per
platform, and a user who can no longer read the thing that is about to run
`sudo pacman -Syu` on their machine. For a tool whose main claim is
trustworthiness, being auditable in a text editor is a feature.

**bash 4+.** Associative arrays and `mapfile` would make several parts shorter.
It costs macOS, which is a third of the platforms in the promise.

**bash 3.2.** Universal on every target, readable, no build step.

## Decision

bash 3.2, with the restriction enforced mechanically rather than by discipline:
no associative arrays, no `mapfile`/`readarray`, no `${var,,}`, no `local -n`.

CI greps for all four and fails the build, and the test suite runs on a macOS
runner as well as Ubuntu — a Linux-only pipeline cannot prove a claim about
macOS.

## Consequences

Some code is longer than it would be otherwise. Lists that want to be
associative arrays are space-delimited strings matched with `case`
(`PARALLEL_SAFE`, `SKIP_LIST`), and per-step timings are a flat array of
`label=seconds` rather than a map.

That cost is paid in this file so it is not paid again in review: the
workarounds carry comments saying which bash 4 feature they stand in for, which
is what stops someone "simplifying" them back.
